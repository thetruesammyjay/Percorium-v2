# Percorium

Percorium is a Solana-first tokenized-stock aggregator. It brings official tokenized stocks and ETFs into one wallet-native experience for discovery, trading, baskets, gifts, portfolio tracking, and social signals.

The product is designed around one simple rule:

> The wallet signs. Percorium prepares, validates, and observes the transaction.

Percorium does not custody user funds or private keys.

## Product direction

- Solana is the default network.
- Official Sunrise-listed stock and ETF mints are the only supported assets.
- Users connect through Privy with Google and Solana wallet support, including Phantom and Backpack-compatible wallets.
- Every transaction is signed by the user’s wallet.
- Percorium charges a 50 bps platform fee.
- Copy masters receive 10% of the Percorium platform-fee cut generated by eligible copy-once trades.
- Base is optional and remains hidden until enabled in Settings.
- The interface is mobile-first, quiet during trading, and expressive in brand surfaces.

## Core capabilities

### Trading

The Solana trading rail supports:

- SOL or USDC to an official tokenized stock or ETF.
- An official stock or ETF back to SOL or USDC.
- Stock-to-stock swaps.
- Limit orders through Jupiter Trigger V2.
- DCA orders through Jupiter Trigger V2.
- Sunrise quote and execution flows.
- A visible fee breakdown before signing.
- Wallet-signed transaction execution and confirmation tracking.

The backend never receives a private key. It returns a validated transaction or order instruction for the connected wallet to sign.

### Baskets

- Custom baskets containing 2–8 official Sunrise mints.
- Weights must total exactly 100%.
- Shareable basket URLs use `/b`.
- Preset baskets are backed by Sunrise-listed index or ETF mints.
- Basket previews show constituents, weights, estimated fees, and expected execution steps.
- Buying a basket is a prefilled multi-leg trade. It does not create an unofficial token.

### Gifts

Gift claims use the `/g` surface:

1. A sender creates a claim link.
2. The recipient signs up with Privy or connects a wallet.
3. A wallet is created or linked.
4. The recipient claims the balance.

Recipients can be addressed by:

- `@handle`.
- A linked `.sol` name.
- A linked `.sns` name when it resolves to the expected public key.

### Identity

- A unique `@handle` is created on first Google sign-in or first wallet connection.
- A user may link an SNS name.
- An SNS link is accepted only when it resolves to the user’s wallet public key.
- Social surfaces display the handle, while the wallet remains the authority for signing.

### Social surfaces

- Leaderboards for Percorium fills over 24 hours and 7 days.
- Callouts limited to 140 characters and tied to an official mint and transaction signature.
- “Copy this buy” creates a prefilled trade ticket.
- Copying never creates an automatic trading bot.
- Private trades do not create public callouts.

### Earn

- LP access is shown only when a real pool exists.
- LP deposits are signed in-app by the connected wallet.
- Lending and borrowing are shown only when the asset exists on Kamino or Jupiter Lend.
- Dead or unavailable markets are hidden rather than presented as empty promises.

### Privacy

- MagicBlock is available as a user-controlled privacy toggle.
- The default is off.
- Privacy state must be visible before an action that changes transaction or execution behavior.

### Charts and news

- DexScreener is the primary chart source.
- Solana pair discovery uses the DexScreener token-pairs API.
- GeckoTerminal is the chart fallback.
- Base follows the same chart abstraction when the Base rail is enabled.
- Finnhub is the only news source.
- Stock pages show company and earnings news.
- Home shows watchlist headlines, falling back to SPY when the watchlist is empty.
- News is cached and links out to the original source.

### Discovery

- Instant search over the Sunrise asset list.
- Per-user watchlists.
- Asset pages are identified by mint address, not ticker alone.

### Agents

The MCP surface is planned after the Solana swap flow is stable. Initial tools will be:

- `list_assets`
- `quote`
- `swap`
- `gift`
- `basket`
- `copy_once`
- `balances`

There is no in-app LLM chat in the initial product scope.


## Architecture principles

### One backend boundary

The web app communicates with FastAPI through `apps/web/lib/api.ts`. Business rules should not be duplicated in React components or Next.js route handlers.

Next.js is responsible for rendering and interaction. FastAPI owns domain validation, external integrations, persistence, fee calculation, and transaction preparation.

### Rail adapters

The product domain should remain chain-neutral where possible:

```text
Asset
Wallet
Quote
TradeIntent
Order
Basket
Gift
Portfolio
```

Chain-specific behavior belongs behind rail adapters:

```text
SolanaRail
├── Sunrise
├── Jupiter Trigger V2
├── Alchemy RPC
└── SPL token account handling

BaseRail
├── 0x
├── Aerodrome Slipstream
├── Chainlink
└── EVM transaction handling
```

The frontend should receive normalized data regardless of the active rail. A quote should identify its rail, asset addresses, expiration, fee, price impact, transaction payload, and signing requirements.

### Wallet-signing flow

1. The frontend identifies the connected wallet.
2. FastAPI validates the requested assets, amount, fee, slippage, and user permissions.
3. FastAPI requests a quote or order instruction from the appropriate rail adapter.
4. FastAPI returns a transaction or order payload with an expiration time.
5. The frontend asks the wallet to sign and submit it.
6. The frontend sends the resulting signature to FastAPI.
7. FastAPI confirms the transaction and updates the user’s trade state.

Wallet addresses, handles, and SNS links must not be trusted from ordinary client input. Wallet ownership must be proven by a signature or by a verified Privy wallet relationship.

### API contracts

FastAPI’s OpenAPI schema is the source of truth for the web client. The project should generate or maintain a typed TypeScript client from the API schema rather than manually duplicating request and response types.

Important API behaviors:

- Use idempotency keys for trade, gift, and order-creation requests.
- Return explicit `pending`, `submitted`, `confirmed`, `failed`, and `expired` states.
- Never return secret integration credentials.
- Include `fee_bps`, `platform_fee`, `network_fee`, and `total_debit` in quote responses.
- Include `expires_at` on every executable quote.
- Keep transaction signatures and external provider IDs for reconciliation.

Example quote shape:

```json
{
  "rail": "solana",
  "sell_mint": "USDC_MINT",
  "buy_mint": "OFFICIAL_STOCK_MINT",
  "sell_amount": "100000000",
  "expected_buy_amount": "123456",
  "price_impact_bps": 42,
  "fee_bps": 50,
  "platform_fee": "500000",
  "network_fee": "estimated",
  "total_debit": "100500000",
  "expires_at": "2026-01-01T00:00:30Z",
  "transaction": "base64-or-provider-payload"
}
```

## Fee model

The platform fee is 50 basis points, or 0.5% of the applicable trade amount.

The fee must be:

- Calculated server-side.
- Displayed before the user signs.
- Sent to the configured Percorium fee wallet.
- Recorded with the trade intent and transaction signature.
- Reconciled after confirmation.

For eligible copy-once trades, the copy master receives 10% of the Percorium fee cut. Copying is always a user-confirmed, prefilled trade and never an automatic execution authority.

## Data sources and external services

| Purpose | Primary source | Fallback or note |
| --- | --- | --- |
| Official Solana stock/ETF list | Sunrise | Reject unknown mints |
| Solana quotes and execution | Sunrise | Route-specific validation |
| Limit and DCA orders | Jupiter Trigger V2 | Persist order state |
| Solana RPC | Alchemy | Configure separate public/private endpoints as needed |
| Charts | DexScreener | GeckoTerminal fallback |
| News | Finnhub | Cache responses and link out |
| Lending | Kamino / Jupiter Lend | Hide when no supported market exists |
| Identity | Privy | Wallet remains the signing authority |
| Optional Base rail | 0x / Aerodrome / Chainlink | Hidden by default |

Every external response must be validated before it reaches a signing flow. Provider availability is not proof that an asset or route is official.

## Design system

[`DESIGN.md`](DESIGN.md) is the visual source of truth. [`Percorium.png`](Percorium.png) is the master logo reference.

The visual system uses:

- Pastel paper surfaces.
- Black cutout-style outlines.
- Electric blue as the primary brand surface.
- Mint, lavender, ember, yellow, and violet sticker accents.
- Large sculptural display type for brand surfaces.
- Aeonik Pro or a close substitute for product UI.
- Pill navigation and buttons.
- Rounded cards without shadows.
- A single restrained motion language: marquee and small interaction transitions.

The product has two visual modes:

1. Brand surfaces use the expressive sticker-book language.
2. Trading surfaces reduce decoration and prioritize price, fee, slippage, signing, and status clarity.

### Brand assets

The brand asset pipeline should provide:

- A vector or simplified logo mark for navigation and favicons.
- A monochrome logo for dense product surfaces.
- Small Sunrise stock and ETF marks.
- Light and dark logo variants where contrast requires them.
- Raster fallbacks for social cards and install surfaces.

### Semantic colors

Decorative sticker colors and semantic state colors are separate systems.

Every state must be readable through color, text, and an icon or status label:

| State | Meaning | UI requirement |
| --- | --- | --- |
| Success | Confirmed or completed | Green semantic token plus explicit label |
| Warning | Action can continue with attention | Amber semantic token plus explanation |
| Blocked | Action cannot proceed | Red or high-contrast danger token plus reason |
| Pending | Waiting for wallet, provider, or confirmation | Violet/blue token plus progress state |
| Neutral | Informational or inactive | Gray/black token plus clear copy |

Do not use the decorative mint sticker color as the only success indicator.

## Local development

### Prerequisites

- Python 3.12 or newer.
- `uv`.
- Node.js 20.9 or newer.
- `pnpm`.
- PostgreSQL for persistent local development.
- Redis if quote caching, rate limiting, or background workers are enabled locally.

### Backend with uv

The API uses `uv` for dependency management and virtual-environment execution. Do not use `pip install` directly for project dependencies.

```bash
cd apps/api
uv sync
cp .env.example .env
uv run alembic upgrade head
uv run fastapi dev app/main.py
```

The API should be available at `http://localhost:8000`.

Useful backend commands:

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy app
uv run python scripts/sync_assets.py
```

To add a backend dependency:

```bash
uv add package-name
```

To add a development dependency:

```bash
uv add --dev package-name
```

Commit both `pyproject.toml` and `uv.lock` when dependencies change.

### Frontend with pnpm

```bash
cd apps/web
pnpm install
cp .env.local.example .env.local
pnpm dev
```

The web app should be available at `http://localhost:3000`.

Useful frontend commands:

```bash
pnpm lint
pnpm typecheck
pnpm build
```

### Running both applications

Run the API and web app in separate terminals:

```bash
# Terminal 1
cd apps/api
uv run fastapi dev app/main.py

# Terminal 2
cd apps/web
pnpm dev
```

Set the frontend API base URL to the local FastAPI service in `.env.local`.

## Testing strategy

### Backend

Backend tests should cover:

- Official mint validation.
- Sunrise quote normalization.
- Jupiter Trigger V2 order payloads.
- Fee calculation and copy-master split.
- Quote expiry and replay protection.
- Wallet signature verification.
- Handle and SNS ownership checks.
- Gift claim state transitions.
- Basket weight validation.
- Portfolio reconciliation.
- API authorization and rate limits.

### Frontend

Frontend tests should cover:

- Wallet connection and disconnection states.
- Trade ticket states and fee disclosure.
- Basket creation and `/b` link handling.
- Gift claim states at `/g`.
- Settings-controlled Base visibility.
- Asset search and watchlist behavior.
- Responsive navigation and keyboard accessibility.

### Integration and transaction tests

Use Solana devnet or provider-supported test environments for transaction construction and confirmation tests. Never use production private keys in local development or CI.

## Security requirements

- Only official Sunrise-listed mints may be quoted or traded.
- Validate mint address, token program, decimals, and asset metadata.
- Wallets sign all user-authorized transactions.
- Backend endpoints must validate authenticated user context.
- Use short-lived quotes and reject expired payloads.
- Use idempotency keys for state-changing requests.
- Rate-limit quote, gift, login, and MCP endpoints.
- Validate all provider responses before constructing transactions.
- Do not trust a client-supplied wallet address without signature or verified wallet ownership.
- Store transaction signatures and reconcile them against the chain.
- Keep private trades out of public social feeds.
- Log security-relevant events without logging secrets or raw personal data.
- Configure strict CORS, security headers, and content-security policy for production.

## Deployment shape

The intended deployment has two independently deployable services:

```text
Browser
  │
  ├── Next.js web service
  │      │
  │      └── FastAPI JSON API
  │              ├── PostgreSQL
  │              ├── Redis / worker
  │              ├── Sunrise
  │              ├── Jupiter
  │              ├── Alchemy
  │              ├── DexScreener / GeckoTerminal
  │              └── Finnhub
  │

```

The API should expose health and readiness endpoints. Background workers should handle provider refreshes, news caching, order status polling, and transaction reconciliation rather than blocking user-facing requests.
